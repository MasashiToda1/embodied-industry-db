# 招聘研发动向

主体页回答「近期在建设什么能力、方向是否发生变化」。不做职位列表或招聘数量排名。

事实仍在 `events/`（`hiring_signal`），研判单独存放于本目录；页面不会根据技能关键词自动生成判断。第一版展示库内已有招聘事实，不新增未经维护者审核的公司研判。公开官网与 Agent-Reach 接入的 BOSS / LinkedIn 都可提供候选，但采集不能直接发布。

## 流程

1. 核验官方招聘职责与来源，按公司别名、平台岗位 ID、原文链接和内容去重；跨平台同一岗位合并来源，不重复计数。
2. 候选材料记录平台 ID / URL、岗位标题、职责原文、明确提供的发布日期、首次发现、最近确认、内容变化及下架情况。未知日期留空；访问失败不能判定下架。历史快照保留，不按当前有效性删除。
3. 向维护者提交：事实、判断、替代解释、尚不能确认的部分及证据强度。单个岗位或长期通用 JD 为有限线索；互补岗位与连续观察可增加支持；独立产品、代码或论文证据才可交叉印证。转载和重复招聘不增加强度。
4. 获准后按现有流程追加招聘事实与快照，研判写入本目录。更新研判新增一条，保持 `topic` 相同；更正也追加，明确说明旧判断为何变化。
5. 仅明显的新方向、能力组合或工程化变化形成新的招聘事件；日常重复抓取留在候选观察记录，不每天制造时间轴事件。

## 研判格式

以下是结构示例，全部占位符必须替换；不作为公司真实研判导出。

```yaml
id: hiring-YYYY-MM-DD-org-topic
org: existing-org-id
topic: manipulation
title: 可能在加强灵巧操作能力
judgment: 这里写经审核的判断，并解释招聘职责之间的联系。
limitations: 这里写替代解释，以及尚不能确认的新项目、落地或投入规模。
strength: limited  # limited / supported / corroborated，证据支持程度，不是公司评分
evidence_events:
  - existing-hiring-event-id
reviewed_on: 'YYYY-MM-DD'
review_reference: 维护者批准的聊天批次或 PR / issue 链接
```

所有引用必须是该公司作为 subject 的已有事件，至少一条为招聘事实。网站构建拒绝未知字段、缺失审核记录、无效或跨主体证据、重复 ID 与无效日期；事实门禁仍不允许推断性摘要。审核引用用于溯源，不能代替实际取得维护者同意。

## 页面口径

- 近 90 天是阅读窗口，不是岗位有效期或研判保质期。按招聘来源的 `retrieved` 日期判断，不用审核日期刷新时效。
- 每个方向显示最近审核的一条；旧版和较早证据折叠保留。最新判断的证据较早时，不回退展示更旧判断为当前。
- 无研判时只展示已有招聘事实；没有近期证据时明确标注信息缺口。
- 招聘核验时间不等于岗位启动时间。技能要求不直接改写技术轴；岗位下架不等于项目停止，岗位数不等于实际招聘人数。
- 所有判断可以展开到事实事件，再查看原始来源和历史快照。研判不会写入事实时间轴、技术栈或关系图。

## 采集边界

公开官网优先；BOSS / LinkedIn 需要人工登录时，仅作为本地只读采集渠道，候选去重后交维护者审核。第一版没有安装这些工具、读取登录态或启用新的自动采集任务。
