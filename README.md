# 具身产业库 · Embodied Industry DB

追踪具身智能产业的主体、技术路线与商业进展。把分散在官网、论文、代码仓库、招聘和商业公告中的信息，整理成可检索、可对照、可追溯的记录。覆盖全球，中文优先。

**[访问网站](https://embodied.menily.ai) · [浏览主体](https://embodied.menily.ai/orgs.html) · [查看技术路线](https://embodied.menily.ai/axes.html) · [提交线索或纠错](https://github.com/MasashiToda1/embodied-industry-db/issues/new/choose)**

这个库帮助你查清三件事：**谁在做什么、公开记录透露了哪些技术选择、什么时候发生了哪些进展。** 数据持续补充；不做公司评分、排名或投资判断。

## 从哪里开始看

| 想了解什么 | 入口 | 可以看到什么 |
|---|---|---|
| 最近发生了什么 | [时间线](https://embodied.menily.ai/) | 产品、融资、合作、交付、论文、开源、招聘等事件及其来源 |
| 某家公司在做什么 | [主体](https://embodied.menily.ai/orgs.html) | 身份、产业层、简介、已记录的技术取值和事件历史 |
| 同一条路线有哪些公司 | [轴 / 收敛](https://embodied.menily.ai/axes.html) | 路线分组地图直接列出公司；点击公司，对照它涉及的路线并追溯来源 |
| 技术路线的记录如何随时间积累 | [轴 / 收敛的流图](https://embodied.menily.ai/axes.html?view=stream) | 按库内首次可见时间观察各取值涉及的主体数 |
| 谁与谁发生过合作或交易 | [图谱](https://embodied.menily.ai/graph.html) | 事件中记录的主体关系，以及可选的共享技术栈叠加层 |
| 谁在投资、谁在采购、落在哪些场景 | [商业信号](https://embodied.menily.ai/signals.html) | 投融资、买方、场景和公开价格；金额只汇总已披露部分，按币种区分 |

网站支持搜索主体、别名、产品名和事件。没有事件的主体也可以在主体列表中展开查看。

## 怎样读这些记录

**先看证据性质，再看技术标签。** 招聘要求表明团队在寻找什么能力，论文表明研究过什么，项目名称只提供线索；它们不能直接证明产品已经采用某种方案或完成部署。记录会保留这些区别，证据不足时不补路线标签。

**路线分组允许一家公司出现在多处。** 同一主体可以研究或使用多种路线，历史记录也会保留。因此图中的公司数不是市场份额，出现某条路线不代表它是这家公司当前唯一的选择。

**流图展示库内记录的时间变化。** 首次可见时间受来源和收录范围影响，不等同于技术首次采用时间；图形变化也不自动构成整个行业收敛的结论。

**日期和缺失项有含义。** 事件保留日、月、季度或年的精度；推导或估计日期附原文时间说明。核验日期与首次发布日期需要区分。没有金额、规模或技术标签，表示当前记录没有足够证据。

**来源可以追溯。** 公开来源记录原文链接、获取日期和仓库内快照；访谈、现场观察等第三方无法公开核验的信息单独标为 `first-party`，记录渠道类型和获取日期。多个同源页面不算独立交叉佐证。

## 收录范围

收录**以通用机器人本体为最终载体的技术与商业主体**：

- 整机本体、运控与小脑、具身基础模型；
- 数据采集与供给、仿真与工具链、关键部件；
- 动作内容、系统集成、场景运营、标准与检测。

纯工业机械臂、AGV、无人机和扫地机不在当前范围内。工厂、景区等非具身产业买方可作为事件中的交易对方记录，不因此建立产业主体条目。

## 数据如何进入库

官网和官方代码仓库用于核实主体与公开项目；产品公告、论文、数据集、招投标、招聘及媒体报道提供事件线索。每条线索都要回到来源核验，再判断身份、时间、事件类型和技术取值。

自动监测会从媒体 RSS、arXiv、Hugging Face、GitHub 等渠道生成候选 issue，**不会直接写入事实层**。解析器和关键词匹配也只提供候选，仍需核验原文。

主体收录深度分为 `stub`、`draft`、`complete`，由事件数量、轴覆盖和时效等规则生成，具体见 [枚举定义](vocab/enums.yaml) 与 [编译器](scripts/compile.py)。这些是资料覆盖标记，不是公司质量评价；主体之间的记录深度并不均衡。

## 提交公司、事件或纠错

在 [Issues](https://github.com/MasashiToda1/embodied-industry-db/issues/new/choose) 选择「新主体」或「手工事件」模板，手机上也能填写。

提供公司名称或官网、发生了什么、时间和来源即可。发现重复主体、错误归属、失效链接或证据不足，也可以开 issue 说明。提交前先搜索已有名称与别名。

批量贡献和直接修改数据请阅读 [AGENTS.md](AGENTS.md)。公开来源须保存原始快照；历史事件只追加，不覆盖或删除；技术轴使用受控词表。PR 需通过 Gate，并附受影响主体的实际编译预览。

## 数据结构与本地使用

| 位置 | 内容 |
|---|---|
| [registry/](registry/) | 主体与数据集身份、别名、账号和身份来源 |
| [events/](events/) | 带时间、来源和证据性质的结构化事件 |
| [snapshots/](snapshots/) | 公开来源的原始快照 |
| [vocab/](vocab/) | 产业层、事件类型和技术／数据／商业轴词表 |
| [docs/](docs/) | 网站前端；数据在部署时生成 |
| `build/` | 编译生成的主体页、数据集页和合并数据，不手工修改 |

需要 Python 3.11+、uv 和 make。也可以使用仓库的 GitHub Codespaces 配置。

```bash
make setup                    # 安装环境与依赖
make site-serve               # 网站预览：http://127.0.0.1:8800
make serve                    # 入库后台：http://127.0.0.1:8790
make preflight                # 门禁、夹具、解析器测试与编译
make preview ORG=unitree      # 查看受影响主体的编译结果
make intake N=12             # 解析 issue，先检查、不写盘
```

入库后台支持官网／微信页面、招投标和论文解析，也支持手工新建事件。确认 issue 解析结果后，可用 `make intake N=12 WRITE=--write` 写入。提交前的本地检查不能替代 PR 上的 Gate。

字段与流程见 [身份层说明](registry/README.md)、[词表说明](vocab/README.md)、[入库契约](AGENTS.md) 和 [设计文档](DESIGN.md)。

### 招聘研发动向

主体详情展示近期核验的招聘线索，帮助观察研发重点和方向变化。经维护者审核的判断会单独标为「研判」，附事实依据与尚不能确认的部分；没有研判时只显示招聘事实。近 90 天为阅读窗口，较早证据和历史研判折叠保留。招聘要求不代表已实现的产品能力，也不会自动改写技术路线。见 [记录与审核规则](research/hiring/README.md)。
