# WorldFailBench Dataset

This repository contains the open-source dataset for the paper:

> **WorldFailBench: Do World Models Understand Policy Failures?**

WorldFailBench evaluates whether *world models* can serve as faithful policy
evaluators — not only predicting **whether** a robot policy succeeds or fails,
but also **how** it fails (failure reason), **when** it fails (failure stage),
and **under what conditions** it transitions from success to failure (failure
boundary). This dataset provides the **simulator ground truth** used to score
world-model behavior: real closed-loop rollouts executed in the
[RoboTwin](https://robotwin-platform.github.io/) and
[LIBERO](https://libero-project.github.io/) physics simulators, together with
success/failure labels, task-stage annotations, and controlled success/failure
boundary cases.

## 1. Evaluation Episodes (`RoboTwin/` and `LIBERO/`)

Each top-level folder groups episodes by **policy (configuration)** and then by
**task**. Every episode records the **first frame of the rollout** (the initial
scene observation) and a JSON file with ground-truth metadata. These episodes
support the *Failure Reason* and *Failure Stage* evaluation tasks described in
the paper.

### 1.1 RoboTwin episodes

`RoboTwin/<policy>/<task_name>/episode_XXX/`

- `first_frame.png` — RGB image of the initial scene (first frame of the rollout).
- `metadata.json` — ground-truth metadata:

```json
{
  "task": "open_laptop",
  "seed": 200000,
  "success": false,
  "instruction": "Pull the lid of the black laptop with smooth matte surface upward.",
  "split": "seen",
  "stages": ["Reach", "Grasp", "Lift"]
}
```

| Field | Description |
|---|---|
| `task` | RoboTwin task name (e.g. `open_laptop`, `place_cans_plasticbox`). |
| `seed` | Random seed used to generate the initial scene. |
| `success` | Ground-truth outcome of the rollout in the simulator (`true`/`false`). |
| `instruction` | Natural-language task instruction given to the policy. |
| `split` | Generalization split of the scene (`seen`). |
| `stages` | Ordered task-specific stage decomposition used for failure-stage annotation (full lists in [Section 3](#3-task-stage-decomposition)). |

- Policies: `pi05`, `pi05-data-20`, `pi05-data-50`, `fastwam`, `lingbot-vla-v2`.
- 20 tasks per policy, 50 episodes per task → 5,000 episodes in total
  (1,774 success / 3,226 failure).

### 1.2 LIBERO episodes

`LIBERO/<policy_variant>/task_XX/episode_XXX/`

- `first_rgb.png` — RGB image of the initial scene (first frame of the rollout).
- `first_rgb.npy` — the same first frame as a raw NumPy array.
- `scene.json` — ground-truth metadata:

```json
{
  "task": "LIVING_ROOM_SCENE2_put_both_the_alphabet_soup_and_the_tomato_sauce_in_the_basket",
  "init_state_id": 0,
  "language": "put both the alphabet soup and the tomato sauce in the basket",
  "suite": "libero_10",
  "success": false,
  "task_id": 0,
  "stages": [
    "Grasp the alphabet soup.",
    "Move the alphabet soup to the basket.",
    "Release the alphabet soup and retreat the arm.",
    "Grasp the tomato sauce.",
    "Move the tomato sauce to the basket.",
    "Release the tomato sauce and retreat the arm."
  ]
}
```

| Field | Description |
|---|---|
| `task` | Full LIBERO task name (scene + instruction). |
| `task_id` | Integer task index within the suite (`task_00`–`task_09`). |
| `suite` | LIBERO suite (`libero_10`, a.k.a. LIBERO-Long). |
| `init_state_id` | Index of the initial state used for the rollout. |
| `language` | Natural-language task instruction. |
| `success` | Ground-truth outcome of the rollout (`true`/`false`). |
| `stages` | Ordered task-specific stage decomposition used for failure-stage annotation (full lists in [Section 3](#3-task-stage-decomposition)). |

- Policy variants: `pi05_data20`, `pi05_data50`, `pi05_data100` (π0.5
  fine-tuned with 20% / 50% / 100% of the training data).
- 10 LIBERO-10 tasks per variant, 50 episodes per task → 1,500 episodes in
  total (1,056 success / 444 failure).

## 2. Failure Type Taxonomy

The *Failure Reason* task annotates every confirmed failure with **one primary
failure type**, adapting the planning/execution distinction of
[REFLECT](https://robot-reflect.github.io/) and Guardian to trajectory
annotation. Labels describe *observable behavior* in the context of the task
instruction, without assuming internal policy causes. There are **three
labels**:

| Label | Definition | Examples |
|---|---|---|
| **Task Planning Failure** | Task-inappropriate choices of targets, subgoals, or their ordering — e.g. omitting a required step, or attempting a subgoal before its prerequisites are satisfied. | Closing a cabinet before inserting the required object, then attempting insertion through the closed door (violates a task dependency even if the closing motion itself succeeds). |
| **Action Execution Failure** | Failure to carry out an *intended* subgoal through motion or physical interaction. | Missing a grasp (gripper closes beside the mug handle and lifts without the mug); dropping a held object during transport; inaccurate placement. |
| **Indeterminate Failure** (`Unjudgable`) | A confirmed failure whose primary type cannot be identified reliably, e.g. because the decisive interaction is occluded. Recorded as `Unjudgable`; these episodes remain in the all-episode denominator. | — |

Annotation rules (see Appendix B of the paper):

- For each confirmed failure, annotators assign **one primary type** and **one
  decisive stage**; when several errors occur, the type follows the *earliest
  clearly supported primary cause*, and the stage identifies the *earliest
  decisive event* preventing completion.
- Stage names are copied verbatim from the task-specific stage lists below; if
  a stage cannot be identified, annotators record it as `unknown`.
- Successful episodes contribute zero failure counts.

The `stages` field of every episode lists the ordered semantic stages of its
task. These task-specific lists define the **vocabulary of failure stages**:
stage-level failure annotations always reference one of these stages (or
`unknown`). The same decomposition is shared by all policies for a given task.

## 4. Boundary Cases (`boundary/`)

The `boundary/` subset supports the *Failure Boundary* evaluation task. Each
**pair** is constructed by starting from a base initial scene and perturbing
**a single scene dimension** — object `position`, `orientation`, or `size` —
in small steps until the policy's outcome flips. A pair therefore contains two
adjacent variants that straddle the success→failure transition:

- `success/` — rollouts from the last scene variant that (mostly) succeeds;
- `failure/` — rollouts from the first scene variant where performance collapses.

Unlike the evaluation episodes above, every boundary episode also includes the
**full rollout video**, enabling frame-level comparison against world-model
generations.

```
boundary/<Simulator>/<dimension>/pair_XXX/
├── metadata.json                 # pair-level boundary description
├── success/
│   ├── episode_000/              # LIBERO sides: episode_000 - episode_009
│   │   ├── rollout.mp4           # full rollout video
│   │   └── scene.json            # episode-level record
│   └── ...                       # 10 episodes per side
│                                 # (RoboTwin sides are numbered episode_001 - episode_010)
├── failure/
│   └── ...
└── success_scene.json            # (RoboTwin only) full scene snapshot of the success variant
└── failure_scene.json            # (RoboTwin only) full scene snapshot of the failure variant
```

Counts: **RoboTwin** 60 pairs (position / orientation / size × 20) with 10
rollouts per side; **LIBERO** 60 pairs (orientation / position / size × 20)
with 10 rollouts per side → **2,400 boundary
rollout episodes** in total. The pair counts match the paper exactly: 60
frozen boundary pairs per platform, 20 per perturbation factor (Appendix C).
The LIBERO pair list and selection criteria are recorded in
`boundary/LIBERO/manifest.json`.

### 4.1 Episode-level record (`scene.json`)

RoboTwin example:

```json
{
  "policy": "FastWAM",
  "task": "place_cans_plasticbox",
  "language": "Lift the hand-sized metallic can and the white patterned brown metal can, and stick them into the rectangular storage box with grooves",
  "variant_label": "plasticbox_size+0pct",
  "perturb_dimension": "Size",
  "success": false
}
```

LIBERO example:

```json
{
  "policy": "pi05_head_finetuned",
  "task": "KITCHEN_SCENE3_turn_on_the_stove_and_put_the_moka_pot_on_it",
  "language": "turn on the stove and put the moka pot on it",
  "variant_idx": 2,
  "variant_label": "moka_yaw+20",
  "perturb_dimension": "orientation",
  "perturb_delta": 20.0,
  "success": true,
  "gripper_action_conversion": "unit_to_native"
}
```

| Field | Description |
|---|---|
| `policy` | Policy that was rolled out. |
| `task` / `language` | Task name and natural-language instruction. |
| `variant_label` | Human-readable label of the perturbed scene variant (e.g. `moka_yaw+20`, `plasticbox_size+20pct`). |
| `variant_idx` | (LIBERO) Index of the variant along the perturbation sweep. |
| `perturb_dimension` | Perturbed dimension: `position`, `orientation`, or `size`. |
| `perturb_delta` | (LIBERO) Magnitude of the perturbation relative to the base scene. |
| `success` | Observed outcome of this rollout. |
| `gripper_action_conversion` | (LIBERO) Gripper action space conversion used by the policy. |

### 4.2 Pair-level record (`metadata.json`)

LIBERO example:

```json
{
  "task_id": 2,
  "base_episode": 0,
  "perturb_joint": "moka_pot_1_joint0",
  "perturb_axis": 0,
  "dimension": "position",
  "success_variant": 0,
  "failure_variant": 1,
  "success_delta": 0.0,
  "failure_delta": 0.02,
  "success_label": "moka_x+0cm",
  "failure_label": "moka_x+2cm",
  "success_count": 10,
  "failure_count": 7,
  "success_rate": 1.0,
  "failure_rate": 0.7,
  "asset_id": "libero/pi05_libero_data20"
}
```

| Field | Description |
|---|---|
| `task_id` / `base_episode` | Task index and base episode from which the sweep started. |
| `perturb_joint` / `perturb_axis` | Perturbed object joint and axis. |
| `dimension` | Perturbed dimension (`position` / `orientation` / `size`). |
| `success_variant`, `failure_variant` | Variant indices forming the boundary pair. |
| `success_delta`, `failure_delta` | Perturbation magnitudes of the two variants. |
| `success_label`, `failure_label` | Human-readable labels of the two variants. |
| `success_count`, `failure_count` | Number of successful rollouts observed on each side. |
| `success_rate`, `failure_rate` | Observed success rate on each side of the boundary. |
| `asset_id` | Identifier of the policy variant used for the sweep (e.g. `libero/pi05_libero_data20`). |

**RoboTwin pair records use a different schema** (they do not contain the
LIBERO-specific fields above such as `base_episode`, `perturb_joint`,
`success_variant` or `asset_id`). Example (`RoboTwin/size/pair_041`):

```json
{
  "policy": "FastWAM",
  "policy_id": "fastwam",
  "task_id": 26,
  "task": "place_cans_plasticbox",
  "dimension": "Size",
  "category": "size",
  "object_axis": "plasticbox_size",
  "success_label": "plasticbox_size+0pct",
  "failure_label": "plasticbox_size+20pct",
  "success_rate_high": 0.7,
  "success_rate_low": 0.2,
  "drop": 0.5,
  "endpoint_gap": {
    "previous_value": 1.0,
    "failed_value": 1.2,
    "signed_change": 0.2,
    "absolute_change": 0.2,
    "unit": "ratio",
    "failed_over_previous_size_ratio": 1.2,
    "relative_linear_size_change_percent": 20.0,
    "relative_linear_size_change_absolute_percent": 20.0,
    "scale_factor_reference": "original object linear dimensions"
  }
}
```

| Field | Description |
|---|---|
| `policy`, `policy_id` | Policy that was rolled out (`FastWAM` / `Pi0.5` / `LingBot-VLA-v2`) and its identifier. |
| `task_id`, `task` | RoboTwin task index and name. |
| `dimension` | Perturbed dimension, capitalized: `Position`, `Orientation`, or `Size`. |
| `category` | Lowercase category of the perturbation: `position`, `rotation` (for orientation), or `size`. |
| `object_axis` | Perturbed scene axis (e.g. `plasticbox_size`). |
| `success_label`, `failure_label` | Labels of the two boundary variants. |
| `success_rate_high`, `success_rate_low` | Observed success rates of the success-side and failure-side variants (10 rollouts each). |
| `drop` | Success-rate drop across the boundary (`success_rate_high` − `success_rate_low`). |
| `endpoint_gap` | Physical change between the two variants. Its keys are dimension-specific: position pairs include `absolute_change_cm`, orientation pairs include `absolute_change_degrees`, and size pairs include the size-ratio fields shown above. |

### 4.3 Scene snapshots (RoboTwin only)

`success_scene.json` / `failure_scene.json` store the complete simulator scene
state (object poses, geometry, etc., under `snapshot.objects`) together with
the perturbed `actor`, `feature`, `value`, `unit`, and `instruction`, so that
both boundary scenes can be **exactly re-instantiated** in the RoboTwin
simulator.

## 5. Intended Use

The dataset provides the simulator ground truth for the three WorldFailBench
evaluation tasks:

1. **Failure Reason** — given the first frame and instruction of a *failed*
   episode (`RoboTwin/`, `LIBERO/`), evaluate whether a world model's rollout
   reproduces the observable error the real policy makes, using the failure
   type taxonomy in [Section 2](#2-failure-type-taxonomy).
2. **Failure Stage** — using the task-specific stage decompositions
   ([Section 3](#3-task-stage-decomposition)) stored in each episode's
   `stages` field, evaluate whether failures in world-model rollouts
   concentrate at the same execution stages as in the simulator.
3. **Failure Boundary** — using the paired variants in `boundary/`, evaluate
   whether a world model reproduces the success→failure transition under the
   same controlled scene change.

---

## 6. Notes

- All episodes are **closed-loop rollouts of real VLA policies executed in the
  physics simulators**, not in world models; they serve as reference ground
  truth.
- `success` labels are produced by each simulator's task success checker.
- Failure-type and failure-stage labels follow the annotation protocol of the
  paper: stage names are copied from the task-specific lists in
  [Section 3](#3-task-stage-decomposition), and unidentifiable stages are
  recorded as `unknown`; unclassifiable failures are recorded as `Unjudgable`.
- Boundary pairs are labeled by the *relative* outcome change across the pair;
  the absolute success rate on the `failure` side may still be non-zero (see
  `failure_rate` in the pair metadata).
